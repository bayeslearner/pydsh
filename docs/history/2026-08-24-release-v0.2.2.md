# Release handoff — pydsh v0.2.2, 2026-08-24

What shipped, how to consume it, and what is honestly still missing.

## Consuming it from prismi3-agent

```bash
uv add "pydsh @ git+https://github.com/bayeslearner/pydsh@v0.2.2"
```

That is the whole install. `plugkit` comes with it, pinned at `v0.1.0` — no
local kernel checkout, no path dependency, no second clone. Verified by
installing into an empty virtualenv and running a real
mount → stream → persist → reload → measure, not by trusting a local install.

```python
from plugkit import Context
from pydsh import LlmService, SessionStore, TokenMeter

root = Context()
await root.plugin(SessionStore)   # ctx.sessions
await root.plugin(LlmService)     # ctx.llm
await root.plugin(TokenMeter)     # ctx.token_meter
```

prismi3 must bring **its own provider adapter** — pydsh ships none by design.
Subclass `LlmAdapter`, implement `stream(options)`, and register it:

```python
root.llm.register_adapter(["deepseek"], MyAdapter(), retry=policy, defaults={"model": "..."})
```

The handle that comes back releases exactly the routes it bound, so a plugin
that unloads takes its provider with it.

## What is real

- `ctx.sessions` — append-only event log, lossless-JSON payloads, derived
  model-visible messages, WAL SQLite persistence proven across two processes.
- `ctx.llm` — adapter registry with all-or-nothing binding, three-layer call
  config (provider defaults < session header < request), per-route retry with
  bounded jittered backoff, and the `llm/stream` waterfall for middleware.
- `ctx.token_meter` — conversation pressure, measured against the surface.
- `pydsh.message` — the shared vocabulary every seam speaks.

130 tests, `uv run pytest tests -q`.

## What is NOT here — read this before planning against it

The goal is full `service-catalogue.md` parity at the service **and**
default-plugin level. Two of roughly thirteen sprints are done. Still absent:

- **the agent loop** (`agent`, `inbox`, `plan_mode`, `system_prompt`) — the
  single biggest gap; nothing here runs a turn.
- the tools seam mapping onto plugkit's `ToolsService`, and its guards
- the storage tier (`storage_domain`, `settings`, `credentials`, the backends)
- session projections (`session_query`, `session_reference`, `session_stats`)
- every provider adapter, and all 17 default plugins
- the app layer (`sdk`, `cli`, `gateway`, the JSON-RPC/WebSocket tier)

So pydsh is adoptable today as a **session log + LLM seam**, not yet as a
replacement for a working agent backend. A prismi3 migration that assumed the
agent loop was present would stall immediately.

## Traps found the hard way

1. **`[tool.uv.sources]` is not development-local.** uv reads `pyproject.toml`
   out of the git checkout when a consumer installs from a tag, so a relative
   path source resolves as a subdirectory of *this* repo and the install fails.
   v0.2.0 shipped that way, was unusable, and its tag was removed. To develop
   against a local kernel: `uv sync && uv pip install -e ../bayeslearner-microkernel`.
2. **A local-path install proves nothing about a release.** The defect above
   was invisible until the tag was installed into a clean venv.
3. **plugkit's `emit` does not contain listener failures.** A throwing observer
   propagates and starves every later listener. `pydsh.dispatch.emit_contained`
   is the post-commit form, and the one place reaching into kernel internals.
4. **Version was forked** between `pyproject.toml` and `__init__.py`; the two
   drifted within one release. `__version__` now reads package metadata.
